Data Encoding

How computers encode characters — from ASCII to Unicode's UTF-8, UTF-16, and UTF-32.

01 — Introduction

Representation vs. Encoding

In the previous room, we learned that everything in a computer is stored as bits and numbers. But how do those numbers become letters, punctuation, and emojis?

Representation is the idea that data lives as bits and numbers in memory. Encoding is the specific, agreed-upon mapping between those numbers and their meanings — for example, which number corresponds to the character "A".

In text, each character is assigned a numeric code, so a string becomes a sequence of numbers that the computer stores and moves around just like any other data.

When you open a file and see gibberish characters, it means the application is reading the bytes with a different encoding than the one used to save the file. The bytes are correct — the interpretation is wrong.

Key Takeaway

Encoding = the agreed mapping between numbers and characters. Everyone reading a file must use the same encoding as the writer, otherwise the text will appear as garbage.

02 — ASCII

American Standard Code for Information Interchange

ASCII is one of the earliest character encodings, created in 1963. It uses numbers 0–127 to represent English letters, digits, punctuation, and special control characters. The original ASCII standard was limited to 7 bits, giving exactly 128 characters. It acts as a small bilingual dictionary between text and numeric codes.

Key Observations

  • Letters are in order: knowing hex/decimal for A (65 / 0x41) lets you derive B (66), Z (90), then a (97), z (122).
  • Digits start at 48 (0x30): digit 0 = 48, digit 9 = 57.
  • Uppercase–lowercase difference is exactly 32 (0x20). A=65, a=97.
  • When a computer reads 42 in a file, it displays B (not the number 42).

Stored as 8 bits per character on disk, the binary blob looks like:

ASCII Limitations — European Languages

ASCII only covers English. With 7 bits you get 128 characters — not enough for Spanish ñ, French é, German ü, Polish ł, etc. ISO/IEC 8859 extended ASCII to 8 bits (256 chars) with regional variants:

  • ISO-8859-1 (Latin-1) — Western European languages (French, Spanish, German, Italian, Portuguese…)
  • ISO-8859-2 (Latin-2) — Central/Eastern European (Polish, Czech, Croatian, Romanian, Slovak…)

Problem: saving a file in Latin-1 and reading it as Latin-2 will corrupt non-ASCII characters. The sender and recipient must agree on an encoding.

Key Takeaway

ASCII = 7 bits, 128 characters, English only. Extended ASCII = 8 bits, 256 characters, one regional variant at a time. The real fix needed a universal standard — that's Unicode.

03 — Unicode & UTF

One Standard to Rule Them All

Arabic needs 250+ characters for ligatures and diacritics. Japanese requires 2,136 Kanji for daily use (JIS X 0208 defines 6,879). Chinese GB 18030-2022 defines 87,887 Hanzi. Regional encodings couldn't scale — we needed one universal standard.

Unicode is a universal character encoding standard that assigns a unique code point to every character from every modern and historical writing system. Unicode 17.0 defines close to 157,000 characters, almost 4,000 of them emoji sequences.

Code points are written as U+XXXX (hex). Because Unicode is a shared standard, a sender and recipient using any Unicode-compatible encoding will display the same characters — no more garbage.

UTF-8, UTF-16, and UTF-32

Unicode defines code points. UTF (Unicode Transformation Format) defines how those code points are stored as bytes. The three main encodings are:

UTF-8

  • Variable-width: 1 to 4 bytes per character
  • ASCII chars (U+0000–U+007F) = 1 byte — fully backwards compatible with ASCII
  • Non-ASCII (e.g. Ω U+03A9) = 2 bytes
  • Complex/emoji (e.g. 🔥 U+1F525) = 4 bytes
  • Most common on the web. Default for HTML, JSON, Linux.

UTF-16

  • Variable-width: 2 or 4 bytes per character
  • Common chars (Latin, Cyrillic, CJK) = 2 bytes
  • Rare chars and emoji need 2 × 2 = 4 bytes (surrogate pair)
  • Used by Windows internally, Java, JavaScript strings
  • Example: 'A' = U+0041, 🔥 = U+D83D U+DD25

UTF-32

  • Fixed-width: 4 bytes per character, always
  • Simple but wasteful — English text uses 4× more space than UTF-8
  • Example: 'A' = U+00000041
  • Easy to index (character N is always at byte 4N)
  • Rarely used in practice

Why UTF-8 Dominates the Web

UTF-8 is backward-compatible with ASCII: any ASCII file is already valid UTF-8. It's also space-efficient for English text (1 byte/char). A webpage mixing English and emoji only pays the 4-byte cost for the emoji — everything else stays at 1–2 bytes.

Key Takeaway

Unicode = the map (code points). UTF = the encoding (how bytes are stored). UTF-8 is dominant on the web: variable 1–4 bytes, ASCII-compatible. UTF-16 is used by Windows/Java. UTF-32 is fixed 4 bytes — simple but wasteful. Always check what encoding a file or stream uses before parsing it.

Vocabulary

Key Terms

  • Encoding — The agreed-upon mapping between numbers and characters (e.g. number 65 → letter 'A').
  • ASCII — American Standard Code for Information Interchange. 7-bit standard, 128 characters, English only (1963).
  • Extended ASCII / ISO-8859 — 8-bit extensions to ASCII (256 chars) for regional European languages.
  • Unicode — Universal character encoding standard covering all world languages, ~157,000 code points.
  • Code Point — The unique number assigned to a character in Unicode. Written as U+XXXX.
  • UTF-8 — Unicode encoding using 1–4 bytes per character. Backward-compatible with ASCII. Dominant on the web.
  • UTF-16 — Unicode encoding using 2 or 4 bytes per character. Used by Windows, Java, JavaScript.
  • UTF-32 — Unicode encoding using exactly 4 bytes per character. Simple but wastes space.
  • Surrogate Pair — In UTF-16, two 16-bit units used together to encode characters outside the basic range (e.g. emoji).
  • BOM (Byte Order Mark) — A special marker at the start of a file indicating byte order and encoding.
  • Mojibake — The garbled text that appears when a file is read with the wrong encoding (e.g. opening a UTF-8 file as Latin-1).
  • Charset — Short for "character set". Often used interchangeably with encoding (e.g. charset=UTF-8 in HTML).

What is the main limitation of ASCII?
It only covers 128 characters — English letters, digits, and basic punctuation. No support for accented characters, non-Latin scripts, or emoji.
What are ISO-8859-1 and ISO-8859-2?
8-bit extended ASCII variants. Latin-1 covers Western European languages (French, Spanish, German…). Latin-2 covers Central/Eastern European (Polish, Czech…). They are incompatible with each other for non-ASCII characters.
What is Unicode? How are its code points written?
A universal standard assigning a unique number to every character from every language and script (~157,000 characters in v17.0). Code points are written as U+XXXX (hex), e.g. U+0041 = 'A'.
What is the difference between Unicode and UTF-8?
Unicode defines the code points (the map). UTF-8 is an encoding that specifies how those code points are stored as bytes in memory or on disk.
How many bytes does UTF-8 use for ASCII characters? For emoji?
1 byte for ASCII characters (U+0000–U+007F) — fully backward-compatible. 4 bytes for emoji and complex scripts (e.g. U+1F525 🔥).
How many bytes does UTF-16 use per character?
2 bytes for common characters (Latin, Cyrillic, CJK Hanzi). 4 bytes (surrogate pair) for rare characters and emoji.
What is UTF-32? What is its main drawback?
Fixed-width encoding: always 4 bytes per character. Simple to index but wastes space — an English text file in UTF-32 is 4× larger than in UTF-8.
Why is UTF-8 dominant on the web?
Backward-compatible with ASCII (no migration needed), space-efficient for English text (1 byte/char), and handles all Unicode characters. It's the default for HTML, JSON, and Linux.
What is mojibake?
The garbled, unreadable text that appears when a file is opened with the wrong encoding — the bytes are correct but misinterpreted.
What is the Unicode code point for the fire emoji 🔥?
U+1F525. In UTF-32: U+0001F525. In UTF-16: surrogate pair U+D83D U+DD25.
