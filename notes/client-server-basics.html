Client-Server Basics

The basics of the Client-Server model — how computer systems provide services to each other on the Internet.

TryHackMe Networking Beginner
01 — The Big Picture

Introduction

Initially, most computers worked alone: they stored their own files, ran their own programs, and didn't communicate. Then organisations started interconnecting systems to share information regardless of distance.

The precursors of the Internet were born: ARPANET, CYCLADES, NPL, NSFNET. Just like in society where people specialize and offer skills as a service, interconnected systems started to specialize too — some became clients (requesting services) and some became servers (providing services).

What This Room Covers

  • Client-Server model
  • DNS, Client, Server, Port, Protocol, Network
Key Takeaway

The whole Internet runs on the client-server model. Your browser (client) asks servers for content. Understanding this model is fundamental for cybersecurity — most attacks target either the client or the server (or the communication between them).

02 — The Pizza Analogy

Pizza Delivery

Alice wants pizza from Luigi's. She tells Bob: "Get me a large pepperoni pizza and a coke." Bob takes the car, drives to Luigi's, places the order. The employee acknowledges and starts making the pizza. Bob returns with the pizza.

This simple process maps perfectly to computer systems. Let's look at each step.

Client & Server

  • Alice = Client — Initiates the request.
  • Luigi's = Server — Serves the resource (pizza / web page).
  • Bob = Browser — Delivers the request and returns the response.

In computer terms: Alice uses a browser (the client) to navigate to a website. The browser requests the webpage, and the server serves it. The client always initiates the request.

Request & Response

If the request is not formatted correctly or the resource is unavailable, you get an error response. Example: Bob returns saying "no pepperoni pizza" or "the server didn't understand the order" (like an HTTP 400/404/500).

Protocol

When visiting a foreign country, language matters. A protocol defines how a client can communicate with a server:

  • Which commands do client and server understand (e.g. the GET command)
  • How a request is structured
  • What syntax is used (e.g. English language)
  • What response to give for each request (e.g. the pizza, or an error)
  • What response to give for faulty requests (e.g. "No pepperoni pizza available")

Port

A port identifies a specific service running on a system. When a client wants to access a service on a server, it must connect using the correct port.

Analogy: Luigi's offers takeaway, dining in, and delivery. Each service uses a different door: door A for takeaway, door B for restaurant, door C for delivery. Similarly, a single server can run multiple services at the same time, each identified by a different port.

DNS — Domain Name Service

Alice only knew the name of the pizza place. She entered "Luigi's Pizza" into a GPS to get the address (coordinates). DNS works the same way: you enter a website name, DNS resolves it to the server's IP address.

  • Website name (e.g. google.com) → DNS → IP address (e.g. 192.168.1.10)
  • Like the address to your home (street, number, city, country) but for computer systems
Key Takeaway

Memorize the analogy: Alice = client, Luigi's = server, Bob = browser, menu/language = protocol, specific door = port, GPS = DNS. This single analogy covers 90% of networking fundamentals.

03 — In Practice

Web Communication in Practice — HTTP

HTTP (Hypertext Transfer Protocol) is a stateless client-server protocol used for the World Wide Web. Each request is processed independently, without the server retaining information about previous requests.

HTTP itself is stateless, but modern websites and web applications implement mechanisms to introduce statefulness at the application level — such as creating a session identifier (stored in a cookie or token) that is sent with each subsequent request.

HTTP Commands (Methods)

In the main specifications that define HTTP (RFC documents), there are 9 core commands:

  • GET — Retrieve a resource from the server (most common).
  • POST — Submit data to the server.
  • PUT — Update a resource.
  • DELETE — Remove a resource.
  • PATCH — Partially update a resource.
  • HEAD — Get headers only (no body).
  • OPTIONS — Ask what methods are supported.
  • CONNECT — Establish a tunnel.
  • TRACE — Diagnostic tool (rarely used).

We'll focus on the two most common: GET and POST.

GET Method

Used to retrieve a resource from the server. When you open a browser and type https://tryhackme.com, the browser constructs the message behind the scenes, including all headers and fields defined in the HTTP specification.

Anatomy of an HTTP Request

  • Scheme — Tells us which protocol was used (HTTP or HTTPS).
  • Host — The name of the host we must resource from.
  • Filename — Which file is being requested from the host (e.g. /index.html).
  • Address — The full IP address the website is hosted at.
  • Status — Indicates whether the request was successful. 200 OK = success; 404 = not found; 500 = server error.

Example URL Breakdown

For https://www.taldrynsec.thm/contact:

  • Scheme: https
  • Host: www.taldrynsec.thm
  • Path: /contact
Key Takeaway

HTTP is the language of the web. Every page you load = a client sends a GET request, the server responds with content + status code. Knowing this is essential because many attacks (XSS, CSRF, SQL injection) abuse HTTP requests.

04 — Wrap-Up

Conclusion

We explored how devices on the Internet offer services to each other. We focused on the client-server model (similar to ordering a pizza): the client initiates the communication, and the server replies.

We then looked at HTTP, the protocol used for websites, and saw a practical example of what a client request and server response actually look like behind the scenes.

Vocabulary

Key Terms

  • Client-Server Model — Architecture where clients request services and servers provide them. The client always initiates the request.
  • Client — A device or program that requests a service (browser, app).
  • Server — A device or program that provides a service (web server, DNS server).
  • Protocol — Rules defining how a client and server communicate (commands, syntax, responses).
  • Port — A number identifying a specific service on a server. One server = many services = many ports.
  • DNS — Domain Name Service. Translates domain names (google.com) into IP addresses.
  • HTTP — Hypertext Transfer Protocol. Stateless protocol for the World Wide Web.
  • HTTPS — HTTP over TLS/SSL. Encrypted version of HTTP.
  • Stateless — Each request is independent, the server doesn't remember previous requests.
  • Session ID — Identifier used to add statefulness on top of HTTP (stored in cookies or tokens).
  • GET — HTTP method to retrieve a resource.
  • POST — HTTP method to submit data.
  • Request — The message sent by the client to the server.
  • Response — The message sent back by the server (content + status code).
  • Status 200 — OK, success.
  • Status 404 — Not Found.
  • Status 500 — Server Error.
  • RFC — Request For Comments. Documents that define Internet protocols.
  • Scheme — The protocol part of a URL (http, https).
  • Host — The domain or IP part of a URL.
